## 0. 首要结论

1. **不得从 Patch_v1.9、v2.0、v2.1、v2.2 或 v2.3 继续修改。**这些版本中的治疗扩展均未得到可靠的实机成功证明，其中多个版本已明确测试失败。
2. **必须从 Patch_v1.8 重新构建。**该版本是当前指定的稳定基线。
3. **本阶段不要一开始就生成正式补丁。**先证明 HotA 1.8.0 运行时确实执行了所定位的治愈代码，再接入原生复活流程。
4. **静态校验不等于功能生效。**过去多次出现“机器码、跳转、PE 节区和 ZIP 全部校验通过，但游戏内只有原版效果”的情况。
5. **HotA.dll、HD_HOTA.dll 等可能在运行时修改 EXE 代码。**仅分析磁盘上的 `h3hota.exe` 和 `h3hota HD.exe` 不足以证明真实执行路径。

## 4. 当前唯一开发目标：第二阶段

### 4.1 涉及英雄

```text
壁垒：乌兰德 / Uland，治疗特长
港口：阿斯特拉 / Astra，治疗特长
法术：Cure，法术 ID 历史资料为37；必须在 HotA 1.8.0 中重新验证
```

阿斯特拉另有一个独立、低风险的数据修改：

```text
初始技能改为：初级智慧术 + 初级水系魔法
其他初始参数不变
```

### 4.2 第二阶段只做什么

只处理仍有至少一只生物存活的兵队：

```text
1. 保留原版治疗效果与解除负面状态效果。
2. 保留乌兰德、阿斯特拉当前 HotA 1.8.0 的治疗特长增幅。
3. 取得游戏实际计算完成的最终治疗量 H。
4. 先用 H 恢复当前首个单位缺失的生命 M。
5. 剩余量 R = max(0, H - 实际恢复的正常生命值)。
6. R > 0 时，使用游戏原生转世重生/复活流程，永久复活该兵队本场战斗中阵亡的生物。
7. 复活必须完全服从原版转世重生的目标限制。
8. 本阶段不允许选择已经全灭的尸体。
9. 本阶段不做高级水系群体治疗对全灭尸体的额外扫描。
```

### 4.3 精确数值示例

生物单体生命为 10，治疗最终数值为 21。

#### 示例 A：首个单位受伤

```text
原队3只，阵亡2只，剩余1只为6/10
正常恢复：4
溢出复活量：17
```

复活结果应与原版转世重生处理 17 点生命完全相同：

```text
增加1只完整生物
再增加1只具有7点生命的生物
```

实际兵队表示方式由原生复活函数决定，不要手工拼接数量与 healthLost。

#### 示例 B：首个单位满血，但整队有阵亡

```text
原队3只，阵亡2只，剩余1只为10/10
正常恢复：0
溢出复活量：21
```

完整 21 点应进入永久复活流程。

#### 示例 C：没有阵亡

```text
当前首个单位受伤，但没有阵亡生物
```

只执行原版治疗；无法使用的溢出量直接浪费。

### 4.4 永久复活

新增复活固定为永久：

```text
无水系魔法：永久
初级水系魔法：永久
中级水系魔法：永久
高级水系魔法：永久
```

水系熟练度仍按原版影响治疗量、群体范围和解除负面状态，但不决定复活单位战后是否消失。

### 4.5 生物限制

不得通过新特长绕过原版转世重生限制。

正确原则：

```text
普通治疗是否合法：走原版 Cure 规则
溢出复活是否合法：走原版 Resurrection 规则
```

例如原版转世重生不能复活的目标，溢出治疗也不能复活：

```text
亡灵
元素
战争机器
不合法的构装体
克隆体
不能永久复活的召唤物
其他 HotA 原生排除对象
```

不要维护一份自制白名单或黑名单；优先复用原生复活目标验证器。若某兵种可以被普通治疗，但不能被转世重生，则正常治疗生效，溢出量浪费。

### 4.6 本阶段不做的内容

以下全部留到第三阶段：

```text
点击已全灭尸体并施放治疗
全灭兵队的目标高亮与鼠标解析
高级水系群体治疗扫描已全灭兵队
尸体相关 AI 估值
尸体相关伤害/复活提示
```

第二阶段成功的唯一目的，是证明：

> 对仍有存活单位的兵队，治疗完成后的剩余数值能够可靠进入原生永久复活流程。

## 5. 第三阶段预留设计

只有第二阶段经用户实机确认后才继续。

第三阶段目标：

```text
1. 单体治疗可以选择原版转世重生允许的全灭尸体。
2. 全灭兵队没有正常生命需要恢复，因此全部治疗量用于永久复活。
3. 高级水系群体治疗在处理存活兵队后，再扫描己方可合法复活的全灭兵队。
4. 亡灵、元素等限制继续完全服从原版转世重生。
5. 完善 UI、AI、提示和自动战斗。
```

设计定位：

```text
土系转世重生：全部法术数值直接用于复活，复活量高。
水系特色治疗：先填补当前伤势，只有剩余量才能复活；数值较低，但始终永久；高级水系可形成小规模群体复活。
```

## 7. 失败与未验证实验总结

本节是给 Codex 的经验库。目的不是继续复用旧代码，而是避免重复犯错。

### 7.1 ELF_TRY1：把静态生物特长第六字段解释为速度

**设计：** 将 type=4 静态生物特长的第六字段当作 speed bonus。  
**结果：** 游戏可进入，但打开英雄面板崩溃。  
**崩溃：** `h3hota HD.exe 0x0069124C`，写地址 `0x0000008D`；`0x8D` 正好是当时相关英雄 ID。  
**教训：**

```text
- 未使用字段不等于可安全扩展字段。
- 英雄ID与英雄对象指针不能混用。
- HeroSpec 解析、面板显示和战斗结算可能走不同路径。
- 不能因为数据表有空字段就假设引擎会安全携带它。
```

后续埃尔芙速度改为更局部的英雄 ID 判定路线，当前稳定基线保留了该效果。

### 7.2 Patch_v1.9：独立 temporaryHP 数组

**设计：** 为 42 个战斗兵队槽位另建临时生命数组和上限数组。  
**实测：** 可以对满血己方部队施放治疗，但看不到临时生命，也没有实际超额承伤效果。  
**教训：**

```text
- 外部数组不进入原生剩余生命、伤害、界面、AI等核心路径。
- 仅修改目标合法性会让法术可点，但不代表效果钩子执行。
- 需要证明真实治疗结算函数被命中。
```

### 7.3 Patch_v2.0：允许负 healthLost 表示超额生命

**设计：** 令 healthLost 为负，使“剩余生命值 = 上限 - healthLost”显示超额生命。  
**实测：** 仍未生效。  
**结构风险：** 原版伤害公式通常假设 `healthLost >= 0`；负数可能导致死亡数量计算异常，甚至反向增加兵数。  
**教训：**

```text
- 不能只修改显示公式或治疗写入。
- 所有物理、魔法、反伤、吸血、复活、AI和预览路径都要支持负值。
- 即使理论数据模型成立，实际 Hook 未被执行仍然没有效果。
```

该路线已废弃，不要恢复。

### 7.4 Patch_v2.1：外围 Cure 后调用原生复活，并试图允许尸体

**设计：** 原版治疗后计算剩余量，再调用原生复活；同时改尸体目标。  
**实测：** 只有原版治疗效果，没有任何复活；全灭尸体也无法成为目标。  
**教训：**

```text
- 包装外围调用点可能不是 HotA 真正执行的治疗路径。
- 修改 CanReceiveSpell 等外围检查，不足以改变点击格子后的实际目标解析。
- 在治疗后再查询复活合法性，可能已经错过正确状态或调用上下文。
- 必须从运行时调用栈证明位置，而不是靠静态函数名猜测。
```

### 7.5 Patch_v2.2 / Patch_v2.3：第二阶段静态 Hook 尝试

**目标：** 仅处理存活兵队溢出复活。  
**状态：** 生成过补丁与静态校验报告，但没有形成可靠的实机成功证据。  
**处理原则：** 视为不可信实验，不作为新基线，也不要复制其注入代码。

### 7.6 平衡性实验，技术上不等于失败

以下功能曾经生成或使用过，后来因为设计或平衡原因撤回：

```text
索姆拉连锁闪电零耗、只跳敌方：用户认为过强，已恢复原版。
阿德拉开局自动高级祝福：已撤回。
罗尼斯开局自动高级祈祷：已撤回。
梅洛迪娅水系魔法零耗：功能曾被用户确认可正常实现，但后来按设计恢复原版幸运特。
```

这些实验说明某些统一耗魔或开战自动施法路线具备可行性，但不能直接套用到治疗复活问题。

## 8. 为什么过去会“静态全通过、实机无效果”

优先排查下列原因：

```text
1. HotA.dll 或 HD_HOTA.dll 在启动时覆盖了 EXE 原始代码。
2. 普通版与 HD 版实际进入不同函数或不同 wrapper。
3. Hook 位于一个存在但当前版本不再调用的旧 SoD 函数。
4. 治疗数值在 HotA DLL 中重算，EXE 中的值只是 UI 或旧逻辑。
5. 参数/寄存器推断错误，条件判断永远不成立。
6. Hook 执行了，但原生 Cure 后续代码覆盖了新增结果。
7. 调用原生复活函数时缺少战斗管理器、施法方、目标状态或正确调用约定。
8. 复活验证器返回的是另一个对象或空指针。
9. HD Mod 使用了另一条目标提示与实际施法路径。
```

因此，Codex 第一轮任务应该是定位与诊断，不是打包。

```text
哪些差异属于阿德拉祝福零耗
哪些差异属于英雄数据或初始兵力
```

### 阶段 C：定位真实 Cure 路径

在 Windows 实机上建议使用：

```text
x64dbg / WinDbg / IDA debugger / Ghidra debugger
```

或制作只用于诊断的轻量日志 Hook。

需要回答：

```text
1. 英雄主动施放 Cure 时，最先进入哪个模块？
2. 最终治疗量在哪个函数、哪个寄存器或局部变量中确定？
3. 乌兰德/阿斯特拉特长增幅在哪一步加入？
4. 目标 healthLost 和 numberAlive 在哪里修改？
5. HD 版与非 HD 版是否走同一逻辑？
6. HotA.dll 是否覆盖或替代候选 0x446220 路径？
```

### 阶段 D：先做诊断版

诊断版不要复活。只在满足以下条件时写一个明确标记：

```text
英雄为乌兰德或阿斯特拉
施放者是英雄本人
法术是 Cure
目标仍有至少1只生物存活
```

标记可采用：

```text
向独立日志文件写一行
在战斗日志追加临时测试文本
临时修改一个无害且可见的数值
```

用户必须先确认该标记出现，才能进入功能版。

### 阶段 E：接入原生复活

确认 Hook 执行后：

```text
1. 在 Cure 前记录目标首个单位缺失生命。
2. 让原版 Cure 完整执行。
3. 读取游戏实际最终治疗量，或计算原版实际恢复量。
4. 计算 overflow。
5. 使用原版 Resurrection 验证器确认目标可复活。
6. 调用原版永久复活函数。
7. 不手工写 numberAlive、healthLost、numberForeverDead。
```

### 阶段 F：只发布第二阶段测试包

此包必须显式标记为测试版，不得声称已经支持尸体：

```text
Patch_v2.4_STAGE2_TEST
```

用户实机确认后，再生成正式 `Patch_v2.4` 或进入第三阶段。

## 10. 第二阶段测试矩阵

### 10.1 必测：满血存活队伍有阵亡

```text
原队3只，每只生命10
战斗中阵亡2只
剩余1只为10/10
施法界面显示最终治疗量 H
```

预期：

```text
H 全部用于永久复活
兵队数量增加
复活后的首个单位生命由原生复活系统正确表示
战斗结束后复活单位保留
```

### 10.2 必测：存活单位受伤且有阵亡

```text
原队3只，每只生命10
阵亡2只
剩余1只为6/10
```

预期：

```text
先恢复4点到10/10
H-4 用于永久复活
```

### 10.3 必测：没有阵亡

预期：

```text
只执行原版治疗
兵队数量不变
```

### 10.4 必测：无效复活目标

选择一个原版转世重生不能复活的兵种进行对照。

预期：

```text
普通 Cure 若原本允许治疗，则只治疗现有单位
溢出量不复活
不得绕过原生限制
```

### 10.5 必测：永久性

战斗结束后检查：

```text
复活单位没有消失
战后兵力与战斗结束前一致
```

### 10.6 本阶段不应通过的测试

```text
整队全灭后点击尸体施放 Cure
```

第二阶段应明确不支持，以免混淆诊断结果。

## 16. 最后提醒

本项目过去最主要的问题不是规则设计，而是**把静态反汇编中的候选地址误当成了 HotA 1.8.0 的真实运行路径**。

Codex 接手后的正确优先级应为：

```text
运行时证据
> 调用约定与参数证明
> 可复现构建
> 静态结构校验
> 最终打包
```

而不是：

```text
先写机器码
→ ZIP校验通过
→ 假定游戏内会生效
```
