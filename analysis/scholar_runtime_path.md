# 科洛尼斯学术特：原生运行路径与实现记录

## 结论

HotA 1.8.0 标准版与 HD 版的原生英雄会面流程均在 `0x004A25B0` 调用同一段学术交换函数。入口寄存器为：

- `ECX`：第一名英雄的 `H3Hero*`；
- `EDX`：第二名英雄的 `H3Hero*`。

静态反汇编与运行日志共同确认：

- 学术等级：英雄结构 `+0xDB`；
- 智慧术等级：英雄结构 `+0xD0`；
- 已学魔法表：英雄结构 `+0x3EA`，共 `70` 字节；
- 原生会面上限取双方学术贡献的较高值；
- 双方必须通过原生魔法书检查；
- 每个接收方向再分别受接收者智慧术上限限制；
- 原生循环逐一检查魔法等级、是否已学、地图/规则限制，并调用原生学习函数；
- 原生提示、法术列表拼接和交换界面生命周期均位于同一函数内。

## 目标英雄与规则

- 英雄：科洛尼斯，英雄 ID `24`，壁垒德鲁伊，原特长为屠戮；
- 初级学术可传授 1—3 级魔法；
- 中级学术可传授 1—4 级魔法；
- 高级学术可传授 1—5 级魔法；
- 科洛尼斯参与会面时，双方接收者受智慧术限制的魔法等级上限均在原生值上 `+1`，最高仍为 5；
- 会面学术上限仍取双方贡献较高者，只有科洛尼斯自己的学术贡献获得 `+1`；
- 两个方向的接收上限分别计算；
- 原生禁用项、重复魔法过滤、魔法书条件和提示流程全部保留。

## 实现点

正式功能只拦截原生函数内四个局部计算点：

1. `0x004A25CB`：第二名英雄的学术贡献，并建立“本次会面有科洛尼斯”标记；
2. `0x004A25DC`：第一名英雄的学术贡献；
3. `0x004A2657`：排序后 `EDI` 英雄的智慧术接收上限；
4. `0x004A267C`：排序后 `EBX` 英雄的智慧术接收上限。

代码放在正式 V1.14 既有 `.luck3` 节的 `0x800..0xFFF` 尾部，逐字节保留该节前 `0x800` 字节的正式幸运机制。没有新增 PE 节，也没有临时篡改英雄的学术或智慧术字段。

## 特长图标

原生高级学术素材来自纯净 HotA 1.8.0 的 `H3sprite.lod`：

- `Secskill.def` 第 `59` 帧：`skill19c.pcx`，44×44；
- `SECSK32.def` 第 `59` 帧：`skl3219c.pcx`，32×32。

DEF 文件名中的技能编号从 1 开始，而 EXE 内的辅助技能 ID 从 0 开始。学术的 EXE ID 是 `18`，因此素材名使用 `skill19*`。TEST02/TEST03 错把第 56 帧 `skill18c / skl3218c` 当作高级学术，实机显示证明它实际是高级土系魔法。正确的 `Expert Scholar`（中文高级学术）是第 59 帧，不是第 58 帧 `Advanced Scholar`（中文中级学术）。

HD Mod 的特长图标位于两个 215 帧 D32F 容器中：

- `_HD3_Data/Compability/#hota15/UN32.DEF`；
- `_HD3_Data/Compability/#hota15/UN44.DEF`。

科洛尼斯对应第 `24` 帧。D32F 可见图像按运行时方向以 180° 存储，写入时需旋转。每帧标称数据块的前 8 字节固定为 `08 00 00 00 00 00 00 00`，属于运行时元数据而非可见像素；必须原样保留，只能替换其后的可见数据。其他 214 帧必须逐字节不变。

`HPS024DR.PCX` 属于英雄小头像槽位，不是特长图标。DIAG01/02 的闪退最初与该错误资源组合同时出现；TEST02 删除头像文件后仍在相同位置闪退，最终证明直接覆盖 D32F 帧首 8 字节才是持续复现的根因。后续构建禁止新增或修改任何科洛尼斯 `HPS/HPL` 头像资源，并必须保留 D32F 帧元数据。

## 初始魔法

科洛尼斯英雄记录：

- 文件偏移：`0x0027A670`；
- 记录大小：`0x5C`；
- 初始魔法字段：记录 `+0x20`；
- 原值：`55`，屠戮；
- TEST02 新值：`54`，减速。

该修改只允许变化四字节法术 ID 与 PE 校验和，完整英雄记录的其他字段必须保持正式 V1.14 原样。

## TEST02 收尾范围

`HOTA_NEW_HERO_V1.2_SCHOLAR_TEST02` 在已验收 TEST01 功能上增加：

- 两个 D32F 容器的科洛尼斯特长帧；
- 两个 HotA 语言 LOD 与一个中文松散覆盖中的科洛尼斯说明；
- 两份 EXE 中科洛尼斯的初始“减速”；
- 保留一次交换诊断日志用于回归。

TEST02 不增加任何包成员，也不修改英雄头像。

## TEST02 失败与 TEST03 修复

用户运行 TEST02 时，在与 DIAG01/DIAG02 相同的新建场景位置闪退。检查发现 TEST02 把每帧完整标称数据块都当作 BGRA 像素写入，覆盖了前 8 字节的 D32F 运行时元数据。该错误不会改变文件大小、帧头、偏移表或 PE，因此此前静态验证未能发现。

TEST03 保留 `08 00 00 00 00 00 00 00` 元数据，只写入后续可见图像数据；其余说明、初始魔法和学术功能不变。

## 原屠戮特长的彻底解除

TEST03 只替换了 HeroSpec 文本与初始魔法，科洛尼斯在两份 EXE 的原生特长表记录仍为：

```text
文件偏移 0x002787E0
03 00 00 00 37 00 00 00 00 ...
```

- 表基址指针：`[0x00679C80] = 0x00678420`；
- 每名英雄记录大小：`40` 字节；
- 科洛尼斯英雄 ID：`24`；
- 第一项 `3`：原生法术特长类型；
- 第二项 `55 / 0x37`：屠戮。

原生法术特长计算函数 `0x004E6260` 先按英雄 ID 定位该记录，然后执行 `cmp dword ptr [record], 3`；只有类型为 `3` 才继续比较法术 ID并计算分级增幅。TEST03 保留类型 `3`，所以详情窗口仍生成 `+20/+16/+12/+8`，实际屠戮增幅路径也没有被切断。

TEST04 只把科洛尼斯记录的第一项从 `3` 改为游戏原生表中已经存在的禁用值 `-1`（`FF FF FF FF`），保留其余 36 字节不变。由此原生函数在类型门槛处直接返回 0：

- 不再生成屠戮的动态分级加成；
- 对任何法术都不再调用科洛尼斯原屠戮特长增幅；
- 学术会面功能继续由四个已验收 Hook 独立实现；
- 该四字节与 PE 校验和可完整回滚到正式 V1.14。
