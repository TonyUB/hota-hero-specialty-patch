# HotA 新增魔法和道具方案文档

**公开案例：寒冰之剑（新道具166）＋凛冬裁决（新魔法82）＋自定义动画107。**

整理日期：2026-11-04。验证环境：Windows、32位 HotA 1.8.0 中文版、HD 运行路径。

本文公开这一条新增道具与魔法的技术路线，供开发者及其使用的 Codex、其他 AI 助手阅读和复用。其他英雄机制、旧经验资料、内部维护文档和未公开源码不在本文范围内。本文不需要任何私有仓库权限，也不依赖私有文件才能理解。

这是一份已验证案例的开发说明，不是适用于任意 HotA/HD 版本的现成补丁生成器。资源格式、函数地址、指令特征和数量限制必须对照使用者自己的合法游戏文件复核。尤其不要把案例自分配的代码地址当成游戏原有空位。

## 2. 先把三类编号分开

| 类别 | 本案例编号 | 对应资源/记录 |
|---|---:|---|
| 道具ID | 166 | `art166`、道具图集第166帧、地图道具子类型166 |
| 英雄可施放魔法ID | 82 | `spell082`、施法选择/扣魔/AI入口 |
| 复用的兵种效果ID | 81 | HotA 原生冻结，原有逻辑保持 |
| 战斗动画ID | 107 | `banim107`、`WJ107.DEF` |

**82不是107。** 魔法、效果和动画是独立编号空间。新增动画107并不等于新增107号魔法；把魔法82映射到原生效果81，也不应把整次施法都改成81。

推荐的数据流为：

```text
装备道具166
  → 魔法可用性查询允许82
  → 魔法书显示82及正式图标
  → 原生施法动作82：合法性检查、扣魔一次、标记本回合已施法
  → 新魔法的效果适配层：逐个敌军调用原生81效果
  → 自定义动画107播放一次＋音效播放一次
  → 交回原生战斗循环
```

## 3. 开发顺序与基底

按下列顺序逐步建立验证点，每步保留可回退的输入：

1. 新增无效果道具，只验证编号、发放、装备/背包和存档重启读档。
2. 装入自定义道具图标、地图对象；用一个简单原生属性验证效果字段。
3. 新增无效果魔法，只验证魔法书、卷轴显示、选择、合法目标、扣魔和回合标记。
4. 单体复用原生效果，确认效果与新魔法编号分离。
5. 扩为群体；处理免疫、抵抗、AI及快捷战斗边界。
6. 接入自定义动画、游戏速度、正式图标与音效。
7. 将临时授予入口替换为正式道具授予，做正反例检查。
8. 核对所有非目标文件/记录/资源，再打包补丁和匹配的独立HD测试环境。

记录输入EXE、DLL、DAT和资源归档的SHA-256；使用 Python、`struct`、`zlib`、`pefile`、Capstone、Keystone、Pillow 等工具时记录版本。不要把后续补丁套到不匹配的输入文件上。

构建目录、独立测试游戏目录、回退目录分开。测试只运行一个HD游戏实例，启动时显式指定游戏根目录为工作目录。缺少工作目录可以导致配置读取失败；应先排查启动方式，再判断二进制是否损坏。

## 4. HotA.dat：以结构解析记录

本案例的DAT头与记录布局如下；整数为小端序，字符串长度以**字节**计：

```text
文件头：'HDAT' + u32(version=2) + u32(record_count)

每条记录：
  length-prefixed name
  length-prefixed path
  u32 string_count
  string_count 个 length-prefixed byte strings
  u8 binary_present
  如果存在：length-prefixed binary
  u32 integer_count
  integer_count 个 i32

length-prefixed bytes = u32(byte_length) + 原始字节
```

本地中文内容使用GBK字节，资源名称使用ASCII。不要把整个DAT当UTF-8文本搜索替换。必须保留未修改记录的原始字节、顺序及未知字段；新增记录时更新总记录数，修改现有记录时不凭空增加数量。

下面的最小读写示例可在自己的DAT上先做无修改往返验证；它只演示格式，不修改游戏：

```python
import struct

def read_hdat(data):
    assert data[:8] == b"HDAT\x02\0\0\0"
    pos = 12
    def u32():
        nonlocal pos
        assert pos + 4 <= len(data)
        value = struct.unpack_from("<I", data, pos)[0]
        pos += 4
        return value
    def blob():
        nonlocal pos
        size = u32()
        assert size <= len(data) - pos
        value = data[pos:pos + size]
        pos += size
        return value
    records = []
    for _ in range(struct.unpack_from("<I", data, 8)[0]):
        begin = pos
        name, path = blob(), blob()
        strings = [blob() for _ in range(u32())]
        assert pos < len(data)
        present = data[pos]
        pos += 1
        assert present in (0, 1)
        binary = blob() if present else None
        count = u32()
        assert count <= (len(data) - pos) // 4
        ints = list(struct.unpack_from("<" + "i" * count, data, pos))
        pos += count * 4
        records.append(dict(name=name, path=path, strings=strings,
                            binary=binary, integers=ints,
                            raw=data[begin:pos]))
    assert pos == len(data)
    return records

def pack_blob(value):
    return struct.pack("<I", len(value)) + value

def encode_record(record):
    strings, ints = record["strings"], record["integers"]
    binary = record["binary"]
    return (pack_blob(record["name"]) + pack_blob(record["path"])
            + struct.pack("<I", len(strings))
            + b"".join(pack_blob(s) for s in strings)
            + (b"\0" if binary is None else b"\1" + pack_blob(binary))
            + struct.pack("<I", len(ints))
            + struct.pack("<" + "i" * len(ints), *ints))

# data = Path("HotA.dat").read_bytes()
# records = read_hdat(data)
# assert data == data[:12] + b"".join(map(encode_record, records))
```

### 4.1 新道具记录

先复制**结构、槽位和字段语义已核对**的普通道具记录，再显式设置新ID与效果。不能只改名称后继承模板的隐藏能力。

本案例的 `art166` 使用9个字符串；可见名称位于字符串1，拾取提示位于2，说明位于7，数值配置位于8。四个附加整数为零。最终数值配置为：

```text
0 # cost
4 # slot type
1 # type
1 # disabled as defaults
0 # add new spells
0 # attack bonus
0 # defense bonus
0 # spell power bonus
0 # knowledge bonus
```

这里的槽位4是本案例已验证的武器槽配置。`disabled as defaults=1` 用于限制默认分发；本案例没有因此获得“任意随机地图/商店/编辑器均可自动生成”的结论。魔法授予由第9节的专用查询实现，不能同时再启用另一套重复授予。

无效果占位阶段，只改DAT和道具资源，已验证运行时道具数量166→167、原生ID166发放、穿脱、四维不变，以及保存后退出进程、重启读档。最终接通魔法授予时才需要对应EXE逻辑。

### 4.2 新魔法记录

本案例 `spell082` 的名称字符串0/1/2统一，字符串6为音效资源名，字符串7是分熟练度说明、学派与标记配置，字符串8是数值配置。

```text

# Spell flags
COMBAT_SPELL ARTIFACT_SPELL BUFF_DEBUFF CREATURE_TARGET NOT_SIEGE_WEAPON
```

```text
-1 # Target stack type
107 # Animation ix
5 # Level
24 24 24 24 # Mana cost
0 # Effect power multiplier
0 0 0 0 # Effect school skill
0 0 0 0 # AI Value
```

这些是本案例参数，不是所有新魔法通用模板。四个耗魔值必须一起处理；魔法书显示24不等于实际扣魔已经验证。`AI Value=0` 也不表示AI会自动使用新魔法，本案例另有合法后备选择入口。

### 4.3 LOD资源归档

对本案例可写的普通资源LOD：头92字节，资源数量在偏移8；每条索引32字节，结构为 `<16s4I>`，即名称16字节、绝对偏移、解压后大小、类型、压缩后大小。普通压缩成员用zlib；重建索引时按归一化名称排序。

新增索引后必须重新计算全部偏移；不能只在文件尾追加数据而留下旧偏移。逐成员解压检查：未改成员内容逐字节相同，新成员能按名称取出且解压长度正确。源归档如使用哈希名称或其他压缩方式，应先识别，不能套用这个普通LOD写法。

## 5. 道具的三套图像与地图对象

| 用途 | 原生资源 | 本案例尺寸/编号 |
|---|---|---|
| 装备、背包 | `artifact.def` | 44×44，第166帧 |
| 提示、奖励 | `artifbon.def` | 58×64，第166帧 |
| 冒险地图 | `ICEA166.DEF` | 64×32，8个帧引用 |
| 地图配套数据 | `ICEA166.MSK`、`objects.txt` | 道具对象类型5、子类型166 |

地图MSK和对象配置属于配套数据，不是第四张图标。帧引用数与独立图像块数也要分开：本案例地图8个引用共用1个静态裸剑图像块，不应宣称已经完成8帧闪光动画。

### D32F道具图集

本地道具图集实际为D32F，不能只看 `.def` 扩展名就按调色板DEF写入。单组容器中，名称字段每帧13字节，偏移字段每帧4字节，扩展一帧会增加17字节的索引区。

本案例的原 `artifact.def` 已有167个帧槽，但最后166号仍是旧图的备用引用；这不等于DAT中已有166号道具。新增记录后需要为第166帧设置自己的资源缓存名称和内容。

本案例D32帧使用32字节几何头，随后8字节私有元数据，再接BGRA像素。新增帧采用已核对的 `08 00 00 00 00 00 00 00` 元数据；修改旧帧时必须保留旧元数据。对应素材的像素按垂直翻转存放，必须独立解码回RGBA确认方向，不应推广成所有D32资源统一旋转。

追加新图像块并重定向目标帧偏移，保留其他帧的名称、图像块和索引语义。独立解码后逐像素核对可见RGBA，透明像素的不可见RGB可单独规范化。

### 地图DEF与锚点

地图使用原生索引色DEF，并按对应画布核对MSK的可访问/遮挡掩码；`objects.txt` 中增加新对象行并更新首行数量，保留旧行。

本案例对象以最右侧格为落点锚点，曾需要在64×32画布内向右平移8像素。这个8像素是本图构图的修正量，不是新道具通用参数。必须在游戏中核对剑与拾取格、遮挡和阴影的位置。

## 6. 魔法需要四套图标

以下尺寸来自本地实际容器；扩展其他游戏版本前仍要读取源文件头。

| 容器 | 画布 | 魔法82对应帧 | 本案例来源 |
|---|---|---:|---|
| `spells.def` | 78×65 | 82 | 羊皮纸图缩放适配 |
| `spellbon.def` | 58×64 | 82 | 羊皮纸图缩放适配 |
| `spellscr.def` | 83×61 | 82 | 羊皮纸图缩放适配 |
| `spellint.def` | 48×36 | 83 | 透明图缩放适配 |

**卷轴 `spellscr` 使用直接魔法ID；界面小图 `spellint` 使用魔法ID＋1。** 不要把偏移规则混用。只替换魔法书大图不足以完成正式图标接入。

本案例保持原生调色板DEF格式。共享图集沿用原调色板，将新图量化到普通颜色区；透明/特殊色索引0—7保留。不能为了新图重排整个共享调色板，导致旧魔法全部变色。

新增或替换目标帧时只追加目标图像块、修正偏移表；其他帧块保持逐字节一致。除数量和索引外，还要检查每行解码长度、裁剪偏移及渲染结果。

兵种状态栏继续使用原生冻结81的状态显示；新魔法图标不等于必须创造一个新兵种状态ID。若自行实现全新状态，则属于另一项开发工作。

## 7. 魔法入口：DAT登记不等于英雄可以施放

本案例运行时魔法总数扩为83，但传统英雄魔法枚举/数组仍围绕0—69构建，70—81中包含兵种能力。必须分别检查注册表、魔法书、已学数组、选择分派和施法动作。

本案例采用**保留旧枚举，再单独追加82**的方法：

- 魔法书普通循环仍走0—69；检查新记录确实存在后，额外查询82。
- 82的可用性从装备查询得到，不访问英雄70字节数组的第82项。
- 魔法列表只多1项，因此列表容量和分配字节数同步增加1个元素；本案例元素步长12字节，分配 `0x348→0x354`。
- 魔法选择分派对82单独分流，不把所有70—81兵种能力暴露给英雄。
- 群体版本先走合法目标预检，再进入原生无需选定单格目标的动作路径。
- 对82的鹰眼处理单独阻断，保留其他魔法的原有路径。

本案例可用的关键定位点如下，**仅作为反汇编搜索与指令核对线索**：

| 模块/位置 | 作用 |
|---|---|
| HD EXE VA `0x0059CD5B` | 魔法书可用性查询；原指令字节 `8A 84 39 30 04 00 00` |
| HD EXE VA `0x0059CDBD` | 旧循环末尾；原字节 `81 FB 30 25 00 00 7C 93` |
| HD EXE VA `0x0059CCDC`、`0x0059CD34` | 列表分配和容量末尾，必须配套修改 |
| HD EXE VA `0x0059EFD4` | 英雄魔法选择分派 |
| HD EXE VA `0x0059F118` | 群体魔法的预检/动作路径分流 |
| HD EXE VA `0x005A0262` | 本案例82专用鹰眼阻断位置 |
| HD EXE VA `0x0043C702` | AI选择后备入口 |
| `[0x00687FA8]` | 本案例运行时魔法表指针；记录步长 `0x88` |
| `HotA.dll` RVA `0x00251150` | 本案例运行时魔法总数，应至少83 |

HotA/HD可能已经接管原函数中的其他位置。例如本案例既有HD Hook `0x0059CD7E` 保持不变。必须先阅读目标的实际指令、跳转、调用者和返回位置，再建立局部分流。

本案例注册的新代码地址如 `0x006FA000` 是补丁自行分配的空间，不是原生API。其他项目应按PE节对齐、节头剩余空间与自己已有补丁重新分配。

## 8. 效果复用：一次施法，多个目标

本案例不重写整套冻结，而是让82继续承担英雄施法身份，只有合法性/效果局部使用原生81。

### 8.1 单体先通

最初的无效果占位只允许存活敌军；下一步将82的目标判定交给原生81。真正施法后在效果回调局部映射到81，将施法上下文的持续时间参数设为3，执行原生效果后恢复上下文。没有伪装英雄ID，也没有修改所有英雄的原生冻结。

本地定位为：

| 模块位置 | 作用 |
|---|---|
| `HotA.dll` RVA `0x00125DB0` | 目标/概率高层回调；原开头 `56 8B 74 24 18` |
| `HotA.dll` RVA `0x00034DA0` | 效果高层回调；原开头 `51 53 57 8B 7C 24 14` |
| EXE VA `0x005A83A0` | 原生目标资格/作用概率查询 |
| EXE VA `0x00444610` | 原生兵队状态应用入口，本案例用于81 |
| EXE VA `0x005A8C60` | 原生状态/施法日志路径 |

这些高层回调含调用框架参数，不能当普通游戏函数随意 `call`。本案例的效果上下文中，`+8` 是魔法号、`+0x0C` 是战斗管理器、`+0x14` 是施法帧、`+0x1C` 是目标、`+0x20` 是继续执行位置；目标回调还使用x87浮点返回。移植前必须核对ABI、寄存器、栈清理和被覆盖指令的完整长度。

原生81提供的物理增伤保留：本地原代码检查冻结持续时间并增加 `base/4`。受击解除、自然递减和免疫继续使用原生路径；不额外增加一套全局伤害乘算。

### 8.2 扩为全体敌军

概念伪代码如下，函数名用于表达职责，不是可直接编译的SDK接口：

```text
on_effect(spell82, cast_context):
    保存本次施法上下文
    对敌方所有存活战斗槽位：
        用原生81查询资格与概率
        按原生概率进行本队判定
        合法且成功时：原生应用81，持续3回合
    恢复本次施法上下文
    可见战斗中：统一播放动画107及一次声音
    返回原生施法继续位置
```

**不能对每队敌军调用完整 CastSpell。** 扣魔、每回合一次施法标记、鹰眼处理和英雄动作由最外层82施法完成一次；内部只应用效果。

本案例每方遍历21个战斗槽位，而不是只遍历冒险军队7槽。战场布局的本地观察值为：兵队起点 `manager+0x54CC`、两方跨度 `0x6EE8`、单队步长 `0x548`；仍须排除死亡、空位、己方及非法类型。

混合免疫应只影响合法敌军；全体免疫应在预检阶段拒绝并不扣魔。不可为了群体效果直接返回“所有目标100%有效”。

### 8.3 AI和快捷战斗

新魔法不会仅凭一条DAT配置就自动获得完整AI。本案例在原生选择失败后增加82的合法后备选择，保留已有法术优先级，检查装备、魔法书、魔法值、当前回合、合法敌军与已有冻结状态。

可见自动战斗和接受快捷结果界面有阶段性实测；完全隐藏的冒险地图快速结算分支没有单独完成全面验证。动画播放必须保留隐藏战斗/不可绘制场景的跳过条件，不能用需要窗口和播放等待的逻辑阻塞结算。

## 9. 装备授予与获取限制

最终授予规则为：

```text
可施放82 = 英雄满足原生施法前提，并在装备栏持有道具166
```

本地英雄装备栏位于 `hero+0x12D`，19个条目，每项8字节：道具ID和附加子类型。查装备栏即可；不要把背包也算成装备。不同构建必须重新核对结构，不依赖未经证明的背包偏移。

将查询接入魔法可用性提供者，而不是把82永久写入70字节的已学数组。否则会同时产生越界、卸剑后仍会魔法、存档污染和学习渠道泄露等问题。正例为“装备剑、没有82卷轴”；反例至少有“剑在背包”和“没有剑、仅有手工构造的82测试卷轴”。

原型阶段曾用卷轴1的子类型82作为授予入口，正式版本已替换为装备166。卷轴图标配套仍保留，供界面显示及限制反例验证；图标存在不代表应将魔法加入随机卷轴池。

本案例保持正常学习/随机生成的枚举边界，并对82保留专用鹰眼阻断。若要新增一种可正常学习的魔法，则还需要独立处理魔法行会、神龛、卷轴、学术、鹰眼、已学/可用数组和存档容量；本文没有把这些渠道全面开放。

## 10. 自定义魔法动画

### 10.1 从无损透明帧生成DEF

使用透明RGBA序列作为母版，不把战斗背景截图烘焙到每帧，也不从有损预览GIF反向制作正式资源。本案例源序列20帧，640×448，适配原生画布800×556。

最终文件为普通DEF：类型 `0x40`、组0、20帧、编码1。普通DEF只有索引色及特殊透明语义；RGBA半透明采用固定空间阈值近似。每帧重新随机生成透明噪点会造成闪烁，因此各帧沿用同一空间阈值图。需要精确连续Alpha时应另行验证支持它的渲染路径，不能把D32F支持推断到所有魔法动画容器。

普通DEF头为4个u32（类型、宽、高、组数），后接768字节调色板；每组有16字节头、每帧13字节名称及4字节绝对偏移。编码1帧有32字节几何头，帧体起始处为每行u32相对偏移，之后为RLE数据。

本案例编码1的关键约束是：**调色板保留索引0—7必须用填充指令编码，即便只有1像素，也不能塞进字面量数据。** 字面量段标记255，后续长度字节为长度减1；填充段为颜色索引加长度减1。独立解码器可以把错误文件还原得完全正确，但游戏原生渲染仍可能把字面量中的透明0画成青色。

验收至少包含：每行完整解码、没有保留色进入字面量、全部像素索引往返相同，以及游戏实际透明显示正常。

### 10.2 注册动画107

从已核对的同类 `banim` 记录复制结构，命名 `banim107`，资源名设为 `WJ107.DEF`。本案例整数配置为 `[0,15,1,0]`，位置类别和透明开关是不同字段：位置值被掩码为低4位，透明字段另左移8位，最终运行时类型271。

不能只把271写进位置字段。加载动画表时也必须同时扩容：原107项→108项，每项12字节；分配大小和总数同步更新。

| 本地位置 | 作用 |
|---|---|
| `HotA.dll` RVA `0x0006E291` | 动画表分配，改为 `108×12` 字节 |
| `HotA.dll` RVA `0x0006E2D2` | 动画总数同步设108 |
| `HotA.dll` RVA `0x0024E064` / `0x0024E068` | 动画表指针 / 数量 |
| `HotA.dll` RVA `0x00073E00` | 原生创建动画对象，本例参数ID107、基础步长100、位置0/0 |
| `HotA.dll` RVA `0x00075040` | 原生播放/等待路径，本例 `(-1,-1,0)` |

沿用原生对象队列、绘制、时钟、等待和清理。群体效果内部使用“原生应用状态与日志，但不逐队播放冻结转场”的分流；外层统一播放一次自定义动画。

### 10.3 速度必须由游戏控制

早期错误路线把动画步长先除以原生速度系数，之后播放器又乘该系数，两者抵消，导致1速、5速看起来一样。

正确路线是保留100毫秒基础步长，让原生播放器应用速度系数一次。本案例实测动画播放段：

| 游戏速度 | 原生系数 | 动画段耗时 |
|---|---:|---:|
| 1 | 1.0 | 约2.43秒 |
| 5 | 0.1 | 约0.27秒 |

本地原生计时位置在DLL RVA `0x000750BC`、`0x000751C2`。本案例自定义对象的步长字段为 `+0x34`；删除逆向补偿即可，不修改全局游戏速度。这些耗时不包含英雄抬手及其他施法阶段。

## 11. 音效：资源入包与实际调用缺一不可

本案例声音来自公开素材 [Strong Gust Blizzard Wind 01](https://sfxmint.com/sounds/blizzard-wind-01)，页面标记CC0；[授权说明](https://sfxmint.com/license)允许使用、修改和再分发。保存素材来源、下载日期、许可及文件哈希；不要把素材自身的CC0许可扩大为整个游戏资源的许可。

原始WAV的SHA-256为 `7c39c0f3b435e8c97a5929b7452c562612d980b829d772b53b5ba2bf9f3630ab`。截取、滤波、统一响度及首尾淡入淡出后，本地资源为2.4秒、22050Hz、单声道、16位PCM WAV，名为 `WJWind.wav`。

本地 `HotA.snd` 布局：

```text
u32 sound_count
每项48字节：name[40] + u32 absolute_offset + u32 payload_size
随后为各RIFF/WAV数据
```

本例新增索引名 `WJWIND`（不带扩展名），旧285个声音的偏移统一增加48，新WAV放在末尾；旧声音载荷逐字节保留。不要将SND误当LOD的zlib资源索引。

**只设置魔法的声音字段、只设置动画声音标签，并没有让本例自定义施法分支真正发声。** 原因是效果适配回调绕过了原生CastSpell的常规音效入口。最终在已有可见动画分支中，显式调用原生异步音效一次。

[H3API](https://github.com/RoseKavalier/H3API) 的 `H3SoundManager::PlaySoundAsync` 可作为公开接口参考，本例实际调用EXE VA `0x0059A890`：ECX为声音名称，EDX为持续参数−1，栈上传入常量3。调用约定必须准确；不要直接套用普通cdecl声明。

保持原动画创建函数的参数、返回对象、寄存器与栈清理；隐藏/快速结算跳过分支不播放声音。最终验证不仅检查“文件在包里”，还检查一次施法只请求一次声音，并从扬声器回采确认确实包含新WAV。

## 12. 二进制修改的移植边界

案例EXE首选基址为 `0x00400000`；DLL首选基址为 `0x10000000`，DLL启用ASLR。上文DLL地址统一写RVA；运行时实际地址为模块基址＋RVA。VA不是文件偏移，文件读写需通过PE节表换算。

- 每个Hook都断言原指令字节、完整指令边界及返回位置。
- 非新魔法ID必须重放被覆盖指令并返回原流程。
- 模块内部跳转使用正确的相对地址或位置无关方式；保存于DLL中的绝对指针需要重定位处理。
- 从可重定位DLL调用固定EXE函数时，本案例使用间接调用；不能直接拼一个在加载后失效的跨模块rel32。
- 代码节、节数、文件/内存对齐、映像大小和权限配套更新；旧重定位项原样保留。
- 说明字符串的指针、编码和生命周期也要核对。DAT说明被运行时提供者覆盖时，改DAT不一定改变实际弹窗。
- 不在渲染/伤害热路径持续写文件；诊断计数只用于证明调用次数，生产逻辑不依赖进程ID或某次运行的内存地址。

## 13. 失败经验与排查表

| 现象 | 本案例原因/正确处理 |
|---|---|
| 新道具只有旧图 | DAT新记录与图集备用帧是两件事；替换目标帧内容及缓存名称 |
| 地图能放物体但位置不对 | 画布锚点、MSK和对象访问格未一致；在游戏中核对拾取位置 |
| 背景变青、透明失败 | 保留调色板索引被写入RLE字面量；必须用填充指令 |
| 自己的解码器通过、游戏仍显示错误 | 文件往返不等于原生渲染语义通过，需要原生资源对照和实测 |
| 新魔法登记但魔法书不出现 | 英雄枚举仍只到69，需要有界追加入口及容量配套 |
| 魔法书出现但无法选择/扣魔 | 选择分派、目标回调和施法动作入口未接通 |
| 群体施法扣多次魔法 | 对每队调用了完整施法；改为外层施法一次、内层只应用状态 |
| 其他英雄/兵种也被修改 | 门控落在全局表或共享原生效果上；把新逻辑限定在82上下文 |
| 1速和5速一样快 | 逆速度补偿抵消原生控制；让播放器应用一次系数 |
| 音效资源存在但无声 | 自定义分支绕过原生音效入口，需要可见施法处一次原生调用 |
| 魔法可以从非预期渠道学到 | 查询层、数组、鹰眼/学术/卷轴等边界未分开处理 |
| 程序打开时报配置错误 | 首先核对启动的EXE、工作目录及是否误开多个实例 |
| 临时测试道具一直出现在正常开局 | 测试发放代码没有与正式初始化分开；卸除临时发放再验证存档 |

## 14. 验证清单与证据等级

### 道具

- 新记录数量、道具ID、三类资源映射一致。
- 无效果占位穿脱时四维不变；简单属性验证后恢复最终设计数值。
- 地图对象、落点、阴影、拾取提示和装备图正常。
- 保存后退出游戏进程，再启动读档；仍可识别、穿脱同一个新ID。
- 卸除临时测试发放代码后，上述持久化仍成立。

### 魔法

- 魔法书、学派筛选、卷轴及小图各自读取正确帧。
- 当前魔法值100→76；只有一个英雄施法动作和一次本回合标记。
- 三支合法敌军持续时间均3；己方不受影响。
- 自然递减观察3→2→1→0；物理受击解除和原生增伤保持。
- 混合免疫只影响合法目标；全体免疫拒绝并不扣魔。
- AI、可见自动战斗、快捷结果与隐藏分支分别记录覆盖情况。
- 无卷轴、仅装备剑时能施放；剑在背包或仅有测试卷轴时不授予。

### 动画、声音与交付

- 动画对象载入20帧、800×556；播放完成且原生动画对象队列清空。
- 同一战前状态分别测试1速和5速，区分动画段和整个施法过程。
- 一次施法一次声音请求，实际扬声器回采有目标风声。
- 原记录、旧图帧和旧声音载荷分别比较，不能只比较归档总大小。
- ZIP逐成员CRC/字节检查；独立HD测试环境与包内对应文件哈希一致。

本例已经做过上述主要分层验证；免疫组合没有穷尽所有生物/宝物，最终换成剑授予后的AI/快捷战斗未重新跑完整矩阵。最新整合阶段验证了图标、装备授予正反例、24点扣魔、群体冻结、实际音效和动画清理；后续录制又确认1速约2.434秒。不要把“之前阶段通过”写成“每次最终打包都完整重测”，也不要把静态分支检查写成已完成隐藏战斗实测。
