## 前置失败与根因

已撤回的 `HOTA_NEW_HERO_V1.06_UI_TEST1` 同时存在两个问题：

1. 魔法书与战场悬停仍显示原生数值，说明选取的静态候选入口没有控制实际可见文本。
2. 对尸体施放治愈时，HD 版在 `0x0065DC42` 访问异常并崩溃。

崩溃根因已经定位：UI_TEST1 把 217 字节显示格式化器写入 `0x0065DCEF–0x0065DE00`，但正式 V1.05 的复活治疗记录状态也位于同一区域：

- `0x0065DD00`：复活记录数量；
- `0x0065DD7C`：受疗记录数量；
- `0x0065DD80`：受疗记录数组。

因此，尸体复活路径进入 `0x0065DC30` 的受疗日志处理器后读取了已被覆盖的记录地址。该失败进一步确认：文件中的连续零字节不能仅凭静态外观当作代码洞，必须同时排除运行时状态用途。

## 本次诊断目的

不再猜测魔法书和悬停文本的上层入口。改为记录正式 V1.05 原生通用法术效果计算函数 `0x004E59D0` 的治愈调用，以便从实际返回地址区分：

- 魔法书数值查询；
- 战场悬停（存活目标）；
- 战场悬停（可选尸体）；
- 其他治愈计算调用。

诊断只匹配英雄 ID 25（尤兰德）、170（阿斯特拉）与法术 ID 37（治愈）。每次匹配调用都先执行完整原生函数，再记录并原样返回其结果。

## 隔离实现

两个 EXE 都从正式 `HOTA_NEW_HERO_V1.05` 重新构建，并在原映像边界新增 `.uidiag` 节：

| 项目 | 值 |
|---|---:|
| 节 RVA / VA | `0x002E7000` / `0x006E7000` |
| 原始/虚拟大小 | `0x1000` |
| 记录器 | `0x006E7000` |
| 透明分发器 | `0x006E7100` |
| 原生序言跳板 | `0x006E7200` |
| 数据区 | `0x006E7300` |
| 日志文件 | `hota_cure_uidiag01.bin` |

原函数入口的六字节 `55 8B EC 83 EC 08` 被替换为跳转至透明分发器；跳板重放这六字节并返回 `0x004E59D6`。不匹配调用直接尾跳原生跳板；匹配调用返回原生 EAX，诊断代码不写入任何既有治愈、复活、战斗日志、动画或音效状态。

每条二进制记录为 40 字节（10 个小端 DWORD）：

1. `UID1` 魔数；
2. 事件类型（1 = 空目标，2 = 非空目标）；
3. 原生调用者返回地址；
4. 英雄指针；
5. 英雄 ID；
6. 法术 ID；
7. 目标指针；
8. 原生基础输入值；
9. 原生返回值；
10. 保留字段。
